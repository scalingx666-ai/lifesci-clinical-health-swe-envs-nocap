# Issue

**Title:** Bound Journey database waits and release connections on cancellation

## Description

.

This bounds every Journey metadata-store wait by one deadline, defined in the new `openmed/structured/store/deadlines.py`. That deadline is the earliest of `transaction(deadline=...)`, the ambient `store_deadline(...)` scope (which accepts a started `RequestBudget` clock), and the `StoreTimeouts` server cap read from `OPENMED_JOURNEY_STORE_TIMEOUT_SECONDS` and `OPENMED_JOURNEY_STORE_LOCK_WAIT_SECONDS`; the unbounded `threading.RLock` is replaced by a `ConnectionCheckout` that returns a value-free `store_busy` instead of blocking. In `postgres.py`, every write and inherited read runs as one bounded unit: `BEGIN` (`READ ONLY` for reads) with transaction-local `statement_timeout`/`lock_timeout` set through `set_config(..., true)` (`SET LOCAL` semantics) and lowered again as the deadline nears. No statement starts and nothing commits after the deadline, SQLSTATE 57014/55P03 map to `store_deadline_exceeded`/`store_busy`, and any failure, timeout or cancellation rolls back, runs `RESET ALL`, restores the search path and clears driver notices, closing the connection instead if it cannot be reset; driver errors are raised outside the driver's exception context so parameter-bearing diagnostics do not travel with them. In `local.py`, SQLite gets the same checkout, a deadline-derived `busy_timeout`, a progress handler that interrupts statements still running at the deadline, a pre-commit deadline check and `CommitStatusUnknown` for an ambiguous `COMMIT`; `ComposedJourneyStore` and `LocalJourneyStore.ingest_graph()` return these as typed codes (discarding newly written bytes except on `commit_status_unknown`), and the PostgreSQL and local Journey store docs describe the behavior.

Breaking: store operations now fail with `store_busy` (or raise `StoreBusyError` from `transaction()`/`close()`) after waiting 5 s for the store connection and are capped at 30 s each instead of waiting indefinitely; raise the caps with `StoreTimeouts(...)` or the two environment variables for long maintenance work such as `integrity_check()` on a large database. PostgreSQL reads now wait for an in-flight write on the same store instead of running concurrently on its shared connection. A SQLite `COMMIT` that fails after SQLite has ended the transaction now returns `unknown`/`commit_status_unknown` instead of `failure`/`transaction_failed`; replay the same idempotent records to reconcile.

Not covered: real PostgreSQL behavior (server-side cancellation by `statement_timeout`/`lock_timeout`, `RESET ALL` through pg8000 or psycopg) is checked only by the opt-in `OPENMED_TEST_POSTGRES_DSN` integration test added here. It was skipped locally because no PostgreSQL server or psycopg is available; offline coverage uses a synthetic SQLite-backed DB-API driver that enforces the armed timeouts. The ingestion ledger stores in `openmed/interop/ingest/store.py` inherit the bounded connection checkout but do not yet arm transaction-local database timeouts, and migrations run on open are not bounded by these caps.
