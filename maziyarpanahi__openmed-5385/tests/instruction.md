# Issue

**Title:** Reload TLS and mTLS credentials without dropping in-flight work

## Description

. Depends on #4436.

This adds one versioned credential-generation provider, `openmed/service/tls_reload.py` (`TLSCredentialProvider`), shared by gRPC TLS/mTLS and REST mTLS. A reload reads a complete candidate from the configured files and validates it without touching the active generation: completeness, bounded reads, PEM parsing, key/leaf match, chain links (and an optional server CA anchor), validity windows with a minimum remaining validity, client CAs that are real and currently valid CA certificates, and a re-read to catch files that change mid-read. Only then is it activated with one reference swap. Any refusal or activation failure keeps the previous generation, and the result is typed and value-free: generation and previous generation IDs, validation and activation state, overlap deadline, outcome, and a reason code. When the client CA changes, a bounded trust overlap (default 300 s, max 24 h) still accepts clients from the outgoing CA, then retires it. At most two generations are retained. Concurrent reloads are rejected with `tls_reload_in_progress`. Readiness reports whether the active certificate and client trust are inside their validity windows.

For gRPC, `GrpcCredentialReloader` in `grpc_security.py` wraps the provider in `grpc.dynamic_ssl_server_credentials`. The certificate-config fetcher hands grpcio a new configuration only when the generation or the overlap state changes, so new handshakes use the active generation while established connections and in-flight streams keep theirs. `serve(tls=reloader)` and `resolve_grpc_listener(tls=reloader)` accept it. `create_grpc_server`/`serve` gain an `options` argument, and the reloader's `grpc.max_connection_age_ms`/`grace` options (default 1 h + 5 min) close old-generation connections after a declared drain window. For REST, `ServiceMTLS` now verifies each request against the provider's current trust generations (the active one plus the overlap one) and records `request.state.mtls_generation_id`. Admitted requests keep their verified identity. The reload triggers are local: `reload()`, `install_reload_signal_handler()` (SIGHUP, which hands off to a thread), and `TLSCredentialWatcher`, which polls file metadata. The watcher is started by the app lifespan when `OPENMED_SERVICE_MTLS_RELOAD_INTERVAL_SECONDS` is set. `OPENMED_SERVICE_MTLS_TRUST_OVERLAP_SECONDS` sets the overlap. Docs are updated in `docs/serving/grpc.md` (Certificate rotation) and `docs/serving/mtls.md`.

Breaking: REST mTLS startup now validates `OPENMED_SERVICE_MTLS_CA_BUNDLE` as a credential generation and refuses to start if the bundle has an expired, not-yet-valid or non-CA certificate, or if every CA in it expires within 5 minutes. Before, such a bundle loaded and then failed on each request. Migration: remove those certificates from the bundle. When no trusted CA is currently valid, REST requests now get `503 not_ready` (`tls_client_trust_unenforceable`) instead of `401`.

Not covered: the REST server certificate is not reloaded in-process. Uvicorn builds its SSL context from file paths at startup, and Python can only load a chain from a file, which would put key material in a temp file. The docs say to restart behind the shutdown drain or use a reloading sidecar, and to stage old+new CAs in `--ssl-ca-certs` for direct TLS. The #3576 drain coordinator and the #3579 mixed-version lifecycle are not on this base, so REST relies on the existing shutdown drain and gRPC on connection age plus grace. gRPC health wiring (#3917/#4190) is not on this base either; `GrpcCredentialReloader.readiness()` is ready for it. Reload counters are exposed through `metrics()`/`report()` but not exported to `/metrics`. Follow-up with #4822: its RPC interceptor re-verifies peers against the listener's static client CAs, so it should read `reloader.provider.snapshot().trusted_generations` once both land.
