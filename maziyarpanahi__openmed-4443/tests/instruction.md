# Issue

**Title:** Apply non-root, read-only security contexts to the base Helm API deployment

## Description

.

The base Helm API deployment now renders hardened pod and container security contexts by default, with or without `journey.enabled`: `runAsNonRoot`, fixed UID/GID `65532`, `fsGroup` `65532`, `readOnlyRootFilesystem`, no privilege escalation, `privileged: false`, all capabilities dropped and seccomp `RuntimeDefault`. The contexts live in `podSecurityContext` and `securityContext` in `deploy/helm/openmed-service/values.yaml`, so they stay overridable; Helm merges them key by key, so weakening one needs an explicit per-key value. To make the read-only root filesystem usable, the chart always mounts `home` (`/home/nonroot`, exported as `HOME`) and `tmp` (`/tmp`, exported as `TMPDIR`) emptyDirs (the new `writableVolumes` block), and mounts the model cache at `/home/nonroot/.cache` with `HF_HOME` and `OPENMED_CACHE_DIR` under it. When `persistence.enabled=false`, a bounded emptyDir backs that cache. The service images (`deploy/docker/Dockerfile` and the matching root `Dockerfile`) now create a `nonroot` user with UID/GID `65532` and end with `USER 65532:65532`, and the root `docker-compose.yml` and the load-test script use the new cache paths. `tests/unit/deploy/test_helm_chart.py` adds a value-free posture checker. It asserts the exact hardened contexts for the default, `ci-values.yaml`, Journey and emptyDir-cache renders, checks that every runtime write path sits on a mounted volume, and flags each explicit weakening override by the rule it breaks (13 negative controls). It also checks that no render contains Secrets, `hostPath`, host ports or host namespaces. `docs/deploy/helm.md` documents the posture, the volume layout, every new values key and an upgrade note.

Breaking: the API container no longer runs as root or writes to its root filesystem, and the cache moved from `/root/.cache/huggingface` to `/home/nonroot/.cache` (Helm `persistence.mountPath`; Compose now uses a new `openmed-cache` volume). Migration: let models download again (or move the old top-level entries of an existing cache volume into a `huggingface/` directory), drop any `extraVolumes`/`extraVolumeMounts` named `home` or `tmp` or mounted at `/tmp`, and set individual `securityContext` keys explicitly only for images that need root or a writable root filesystem. The Journey API pod now reads the same values keys instead of hard-coded contexts, with the same hardened defaults.

Not covered: the rendered manifests were not applied to a live cluster or schema-validated (no cluster or kubeconform available), and the full service image was not rebuilt. The `groupadd`/`useradd`/`USER` layer was checked on a cached Debian 13 slim base: it ran as `65532` under `--read-only --cap-drop=ALL` with a named volume at `/home/nonroot/.cache`. The `docs/` MkDocs build was not run because MkDocs is not installed in the shared venv.

Validation: `helm lint deploy/helm/openmed-service` with default, `ci-values.yaml` and Journey values (pass), `helm template` for the same renders (pass), `pytest tests/unit/deploy tests/unit/service/test_docker_compose.py tests/unit/mcp/test_mcp_container.py tests/unit/service/test_postman_collection.py tests/integration/test_distroless_image.py -q` (111 passed, 1 skipped), `ruff check .` and `ruff format --check .` (clean), `scripts/security/check_effect_paths.py --check` (verified), `mypy` (clean), `pytest tests/ -q -m "not slow and not fuzz" --ignore=tests/unit/training/synthetic/test_dicom_overlays.py` (26195 passed, 222 skipped, 298 deselected; the ignored module needs `pydicom`, which the shared venv lacks).
